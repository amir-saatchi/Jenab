# Code design — questions
**Status:** Draft, started 2026-09-30

Questions to answer before writing the high-level code (packages, types, interfaces, main functions). Each one points to the SPEC section it comes from. A *lean* is a first thought, not a decision.

## 1. Packages and boundaries
1. What are the top-level packages, and which may import which? For example, the data layer must never import the agent loop.
   **Decided (2026-09-30):**
   ```
   go.mod
   cmd/desktop/         main: builds everything, starts Wails
   internal/
     id/                typed IDs and the ULID generator (added in CODE-OUTLINE)
     logfile/           rotating log file and slog setup (Q36)
     workspace/         the linked folder and its rules (8.5)
     proc/              child processes: Job Object, memory cap, tree kill
     mcp/               MCP client and server processes (Phase 5)
     app/               Wails services and events, no logic (Q3)
     agent/             orchestrator, turn loop, context builder, subagents, schema agent
     provider/          Provider interface; provider/anthropic, provider/openai (also Ollama and compatible)
     tool/              tool registry and the built-in tools
     chat/              Chat, Message, Part, SessionNote and their IDs (Q5)
     project/           open, idle, close, lock and recovery; owns a project's stores
     store/             writer goroutines, reader pools, migrations, change log, undo
     sqlguard/          the three-layer SQL guard (2.2)
     bucket/            ObjectStore and the local folder backend (4)
     config/            YAML, JSON Schema, validation before saving (10)
     view/              view and form runtime (5)
     pipeline/          pipeline runner and step catalog (6)
     expr/              expression sandbox (6.4)
     script/            Starlark child process (SPIKE-016)
     schedule/          cron, DST rule, wake checks (6.2)
     web/               search sources, page fetching, readable text (6.5)
     secret/            keychain
     limit/             Gate: shared limits with two priorities (Q19)
     update/            self-update (2.8)
   frontend/            React + TypeScript, built with Bun and Vite
     embed.go           package frontend: embeds dist/ for main
     src/               the UI; starts from mockups/src
     bindings/          generated by Wails from app/, never edited
     dist/              build output, not in git
   build/               Wails build files: icons, manifests, Taskfiles
   ```
   - Imports go one way: `app` → `agent`, `pipeline`, `view` → `tool`, `provider`, `store` → `sqlguard`, `bucket`. Nothing imports `app`, and a lower package never imports a higher one.
   - The frontend talks to Go only through the generated bindings (calls) and events (streams, results).
   - `frontend/embed.go` is needed because `go:embed` can't reach a parent folder from `cmd/desktop`. The Wails Taskfile builds `./cmd/desktop` instead of the root.
   - No folder or package is named after the app, so a new name only changes the module path, the binary name (one Taskfile variable) and one Go constant.
2. One Go module with everything under `internal/`, or more than one module?
   **Decided:** one module. One app, one release, no outside users; `internal/` keeps the API ours to change. No `pkg/`.
3. Is the Wails layer one thin package that only binds services and forwards events, with no logic of its own?
   **Decided:** yes. The logic is testable without Wails, and a Wails upgrade (pinned beta) touches one package.
4. The script child process (SPIKE-016): the same binary started with a flag, or a second binary?
   **Decided:** the same binary with a hidden flag (`--script-worker`). One file to sign and update (2.8), and the worker's version always matches.

## 2. Structs: the core types
5. What are the core types? Candidates: Project, Chat, Turn, Part, ToolCall, Memory, Pipeline, Step, Run, View, Page, Form (2.3, 6, 5).
   **Decided (2026-09-30):** types live in small packages at the bottom, named by area. No `model` package.
   - `chat`: `Chat`, `Message`, `Part` and its kinds, `SessionNote`, IDs. Used by store, agent and app.
   - `config`: the parsed `View`, `Page`, `Form`, `Pipeline`, `Step`, with their validation.
   - `store`: types that exist only for saving, such as `Run`, `ChangeEntry`, `Memory`, `Approval`.
   - The runner stays in `pipeline` and reads `config.Pipeline`, so `store` and `pipeline` never import each other.
6. One struct per use, or separate types for the database row, the domain and the frontend? Wails generates TypeScript from the structs it binds.
   **Decided:** one struct where it fits. `store` scans rows into it with hand-written SQL (no ORM, no row structs), and services return it, so a renamed Go field shows up as a TypeScript error. A separate view struct in `app` only when the UI needs another shape or must not see a field.
7. A turn is a list of parts (8.3). One `Part` struct with a `Kind` field, or one type per kind behind an interface?
   **Decided:** one struct with `Kind` and one pointer field per kind (`Text`, `Thinking`, `ToolCall`, `ToolResult`, `Image`, `Notice`, `Approval`, `Question`). JSON, the generated TypeScript and the database stay plain; `Validate()` checks that exactly one field is set. `thinking` was added to SPEC 2.3.
8. Typed IDs (`type ChatID string`) or plain strings?
   **Decided:** typed (`type ChatID string`), ULIDs as in 2.3. The compiler catches a chat ID passed as a project ID; TypeScript sees plain strings.
9. Which types are only in memory, such as a running turn or a stream?
   **Decided:** a running turn, a stream event, a write request and a background task stay unexported in the package that runs them (`agent`, `provider`, `store`), and are exported only when another package needs them.

## 3. Interfaces: what is swappable
10. `Provider` (3.8): what are its methods? For example `Stream(ctx, Request) (Stream, error)`, plus the model list.
   **Decided (2026-09-30):**
   ```go
   type Provider interface {
       Stream(ctx context.Context, req Request) iter.Seq2[Event, error]
       Models(ctx context.Context) ([]ModelInfo, error)
   }
   ```
   - `Stream` is a Go iterator: no channel to close, no goroutine to leak; breaking the loop or cancelling `ctx` ends it.
   - Events: text delta, thinking delta, finished tool call, usage, stop reason. The stream applies the 3.8 truncation rules itself: it ends with a stop reason or an error.
   - Implementations: `provider/anthropic` and `provider/openai` (OpenAI, Gemini, Ollama and compatible APIs by base URL).
11. Tools: one `Tool` interface for built-in tools, MCP tools (8.7) and subagents, or separate ones?
   **Decided:** one interface.
   ```go
   type Tool interface {
       Spec() Spec                                          // name, description, argument schema, effects
       Run(ctx context.Context, call Call) (Result, error)
   }
   ```
   - `Spec` declares the tool's effects (reads, writes the database, network …), so the orchestrator decides approvals in one place (8.8).
   - MCP tools get an adapter in Phase 5. The subagent tool is written in `agent` and registered there.
   - Pipeline steps are not tools: they run without a model and have their own small interface in `pipeline`.
   - **Future tools (2026-09-30):** a tool whose needs depend on its arguments has an optional `Preflight(call) (Needs, error)`: `fetch_page` (new host), `mcp_call` (`readOnlyHint`), `run_command` (pattern), `edit_file` (path). Two more effects: `Untrusted` (the result is outside data; the turn is then marked, and later non-read-only calls ask again, 8.5, 8.7) and `NoUndo` (changes outside the app, such as MCP).
   - `store.Undo` takes `Restorer`s for targets outside the database (`file:<path>`, Phase 6), so `store` never writes into the user's folder.
12. What else sits behind an interface? Candidates: `ObjectStore` (4.8), search sources (6.5), the keychain, the clock (for scheduler tests).
   **Decided:**
   - Yes: `ObjectStore` (S3 later), `web.Searcher` (Tavily, SearXNG, keyless sources), the keychain (get, set, delete; tests never touch the real one), the wake detector (a fake sends "resumed").
   - No clock: schedule functions take `now` as a parameter, and goroutine timing is tested with `testing/synctest`.
   - No interface for `store`, `sqlguard`, `config`, `expr`: tests use real SQLite in a temp folder, since the spikes showed its exact behaviour matters.
13. Go defines an interface where it is used, not where it is implemented. So which package owns each one?
   **Decided:** extension points with several backends live with their types: `provider.Provider`, `tool.Tool`, `bucket.ObjectStore`, `web.Searcher` (like `database/sql/driver`). Small test seams (keychain, wake detector) are defined in the package that uses them.
14. Which interfaces exist mainly for tests, such as a fake provider for the scenario runner (TASK-001)?
   **Decided:** no extra ones. `provider/fake` plays scripted events for agent-loop unit tests (no network, same result every run); fake tools give recorded results with delays for TASK-001, which still uses real models.

## 4. Goroutines and channels
15. Which goroutines live for a long time, and who starts and stops each one? Candidates: one writer per database (7.2), the scheduler, one loop per running turn.
   **Decided (2026-09-30):** every goroutine has an owner that can stop it and waits for it; no `go func()` without one.

   | Goroutine | How many | Owner | Stops when |
   |---|---|---|---|
   | Scheduler (minute check, wake events) | 1 | app root | the app quits |
   | Update check (every 6 h) | 1 | app root | the app quits |
   | `project.db` and `chats.db` writers | 2 per open project | `project.Project` | idle (10 min) or close |
   | Chat runner | 1 per chat with work | `agent` | the chat has nothing left to do |
   | Background task, pipeline run | 1 each | `agent`, `pipeline` | it finishes or is cancelled |
   | MCP stdio server (Phase 5) | 1 per server per project | `mcp.Manager` | `Project.OnClose`, or 10 min without calls |

   Reader pools are connections, not goroutines; `registry.db` has one connection and no goroutine.
16. One goroutine per running turn, or per chat? How do a background task and its finish notice fit in (8.3)?
   **Decided:** per chat, only while it has work. The chat has an inbox (user messages, finish notices, *Stop*); its goroutine runs turns one at a time and checks the inbox between steps, which gives the 8.3 rules without locks. Background tasks run on their own goroutines (at most 3 per chat) and send their notice to the inbox. The tool calls of one model response run in order.
17. How does a stream travel from the provider to the screen: provider, orchestrator, Wails events, UI? Through channels? With what buffer, and what happens when the UI is slow (SPIKE-022)?
   **Decided:** provider iterator → chat runner (same goroutine) → coalescer, at most one Wails event per ~16 ms, with a short timer for the rest when tokens pause (5.8) → React buffer, painted once per frame. Finished parts go to the `chats.db` writer. `Emit` never blocks, so the coalescer caps the rate.
18. Write requests (7.3): a channel of typed requests, each with a reply channel? How are the two priorities built?
   **Decided:** yes. The writer reads two queues (interactive, background) with the 10:1 rule; each request has a reply channel with room for one answer, so the writer never waits on a caller that left. Callers see plain methods (`store.Insert(ctx, …) (Result, error)`) that wait for the reply or `ctx.Done()`, on their own goroutine. Wails runs each call from React on its own goroutine with a cancellable `ctx`, so the UI never waits (7.1).
19. Limits such as `max_parallel_calls` and `max_parallel_runs` (7.6): semaphores, or `errgroup.SetLimit`?
   **Decided:** our own `limit.Gate`: N slots, two priorities with the 10:1 rule, first come first served within a priority, and `ctx`-aware. Used for LLM calls (interactive and background, 7.6) and pipeline runs (one priority; a wait past the timeout is `skipped`, 6.2). Background tasks per chat are a counter in the chat runner. No new dependency.
19a. Can a chat, Mother or the developer see what the goroutines are doing?
   **Decided:** Go can't look up a goroutine, so each owner keeps status records.
   - Each owner has `Status() []Status`: task table per chat (ID, kind, state, started, last activity, progress, error), `Stats()` per writer (queue length per priority, current request and its age, done count, last error), slots and waiters per `limit.Gate`.
   - A panic is recovered at the goroutine boundary (Q26) and recorded as failed; the writer keeps serving. A heartbeat per loop flags anything that hasn't moved for longer than its limit.
   - `project.Activity()` collects them into one snapshot. `task_status` (8.3), Mother's chat list (8.6) and the Runtime panel (8.4) read it, each at its own level of detail.
   - Goroutines are labelled with `pprof.Do` (chat ID, task ID), so a goroutine dump shows who owns each one.

## 5. Context and cancellation
20. What does the context tree look like: app, project, chat, turn, request or tool call? What exactly does *Stop* cancel?
   **Decided (2026-09-30):**
   ```
   app                              cancelled at quit
   └─ project                       cancelled when the project closes
      ├─ chat runner
      │  └─ turn                    ← Stop cancels this
      │     ├─ provider request     + its timeout
      │     ├─ tool call            + its timeout
      │     └─ subagents of the turn
      ├─ background tasks           (not under the turn)
      └─ pipeline run
         └─ step                    + step timeout
   ```
   *Stop* cancels the turn and its subagents; pipeline runs and other chats' turns keep going. Open tool calls get a "cancelled by user" result, and streamed text is kept, marked as stopped (SPEC 8.3).
21. A write is already queued when its turn is cancelled. Does it still run?
   **Decided:** "cancelled" means "not done". Still queued: the caller gives up and the writer skips it. Already taken: it finishes and the caller waits for the result. The state switch is atomic (SPEC 7.3).
22. Background tasks outlive the turn that started them. Whose context do they use?
   **Decided:** the project's, like scheduled runs. Not `context.WithoutCancel`, which would outlive the project.
23. Where are the timeouts set: reader queries (2 s), provider calls, Ollama (minutes)?
   **Decided:** where the work starts, with `context.WithTimeout`; never stored in a struct.

   | What | Limit |
   |---|---|
   | View query / agent `query`, `db.query` | 2 s / 10 s (2.2) |
   | Tool call | per tool in its `Spec`, default 60 s |
   | Pipeline run / step | 5 min / 60 s; waiting for writes doesn't count (6, 7.5) |
   | Approval wait | none (8.8) |
   | LLM request | first event 2 min (Ollama 10 min), then 60 s between events; no total (3.8) |

   The expression engine can't be cancelled: its 1 s watchdog only stops the waiting, so its size and nesting limits bound the work (6.4). Scripts run in a child process that is killed.

## 6. Errors
24. Which errors must the code tell apart? Candidates: `ProviderError` with quota and truncation (3.8), approval denied (8.8), config errors with paths (10), SQL guard rejections (2.2).
   **Decided (2026-09-30):** sorted by what happens next.

   | Kind | Examples | What happens | Go form |
   |---|---|---|---|
   | Retried quietly | rate limit, transport, 5xx, cut-off stream | retried with backoff in the provider layer (3.8) | `*provider.Error` with `Kind`, `RetryAfter` |
   | Blocks the model | wrong key, daily quota, stalled | the turn ends; the user gets a card | `*provider.Error` |
   | Shrinks the context | 413 | not retried as is; the context is shrunk | `*provider.Error`, `TooLarge` |
   | Model can fix it | bad arguments, SQL guard rejection, config errors, not found, revision conflict, tool timeout | back to the model as an error `tool_result` | `*tool.Error` |
   | User decided | approval denied (with note), *Stop* | the tool result for the model | a normal `Result` |
   | System failure | disk full, damaged database, bug, panic | model gets "internal error, tell the user"; user gets a card with *Copy details*; logged | any other `error` |

   - Sentinels for plain conditions (`store.ErrNotFound`, `store.ErrConflict`); types for errors with data (`provider.Error`, `sqlguard.RejectError`, `config.Errors` with path, line and column).
   - `errors.Is` / `errors.As`, never string matching. Each layer wraps with `%w` and some context.
   - Log or return, never both: errors are logged once, at the goroutine boundary (chat runner, writer, pipeline run, Wails service).
25. Which errors go back to the model as a tool result, and which go to the user?
   **Decided:** the model gets only what it can act on: what it can fix and what the user decided. Blocking provider problems and system failures go to the user. Secrets are removed from every message (6.7). `app` turns known kinds into short plain-English text; anything else is "Something went wrong" with *Copy details*.
26. Where are panics recovered?
   **Decided:** at every goroutine boundary from Q15 (chat runner, task, pipeline run and step, each writer request, scheduler tick, our Wails services; we don't rely on Wails' own handler). The stack is logged, the item is marked failed (Q19a), the user gets a card, the app keeps running. A writer that panics mid-transaction rolls back, closes and reopens its write connection, then continues.

## 7. Generics
27. Is there a place where generics clearly help, such as a typed request and reply for the writer queue (`Request[T]`)? Or do we avoid them until a need shows up?
   **Decided (2026-09-30):** only where the same code runs for many types. Three helpers:
   - `store.Do[T](ctx, w, prio, func(tx *sql.Tx) (T, error)) (T, error)`: a typed write with a typed result; the queue itself holds a plain `job` interface.
   - `store.Query[T](ctx, pool, sql, args, scan) ([]T, error)`: row scanning with `rows.Close`, `rows.Err` and the timeout in one place.
   - `tool.Func[A](spec, func(ctx, A) (tool.Result, error)) tool.Tool`: checks the JSON arguments against the schema, decodes them into `A`, and returns a `*tool.Error` if they're wrong.
   - Standard generics (`slices`, `maps`, `cmp`, `sync.OnceValue`, `iter`) freely.
   - Not in anything Wails turns into TypeScript (it skips generic services), not for IDs, not for `limit.Gate` or status types. `any` only at the JSON edge (`json.RawMessage`).

## 8. Wiring and lifecycle
28. How does `main` build everything?
   **Decided (2026-09-30):** plain constructors in one place, no DI library, no globals, nothing started in `init()`. `main` calls `run(args) error`, which checks the script-worker flag (Q4), loads `config.toml`, builds the packages in import-graph order and starts Wails. A constructor with more than about 3 dependencies takes a small `Deps` struct.
29. Opening, idling and closing a project (2.7): does a `Project` value own its writers, reader pools and schedules?
   **Decided:** a `Project` owns its storage: both writers, both reader pools, the bucket and `jenab.lock`. Chat runners and runs stay in `agent` and `pipeline` and hold a lease while they work: `p, err := projects.Open(ctx, id); defer p.Release()`. `project.Manager` keeps one instance per project and runs crash recovery on open. Idle means no leases for 10 minutes; the scheduler takes a lease for each run.
30. Shutdown order: stop turns, drain the writers, checkpoint, close. Who runs it, and how long may it take?
   **Decided:** the app root, in reverse construction order, within Wails' 10 s `OnShutdown` (2.8):
   1. Stop new work (scheduler, new turns).
   2. Cancel the app context: turns end as with *Stop*, runs become `interrupted`. Up to 5 s.
   3. Drain the writers (taken requests finish, cancelled ones are skipped). Up to 3 s.
   4. Per project: `wal_checkpoint(TRUNCATE)` with the 100 ms busy timeout, close the databases, remove `jenab.lock`.

   Past the deadline the app exits anyway; the lock file triggers crash recovery on the next start (2.7). Idle close runs steps 3–4; the update restart (only when idle) runs 1, 3 and 4. Closing the window while in the tray is not quitting.

## 9. The frontend boundary
31. Which Go services are bound to the frontend? One per area, such as chats, pages, pipelines and settings?
   **Decided (2026-09-30):** one thin service per area in `app`: `ProjectService`, `ChatService`, `PageService`, `PipelineService`, `BucketService`, `SettingsService`, and `DevService` (bound only with the developer tools on). Methods take `ctx` first and return typed structs and an error. Long work returns an ID at once; progress comes as events. Files and images go through the asset handler `/objects/<project_id>/<key>` (4.7), not bindings.
32. How are events named, and are their payloads typed structs?
   **Decided:** typed with Wails' `RegisterEvent[T]`, which also generates their TypeScript types. Names are `area:what` (`chat:delta`, `chat:part`, `chat:status`, `run:status`, `project:notice`, `project:activity`), and every payload carries its IDs.
   - **Snapshot plus sequence:** each chat (and run) has a counter that goes up with every change. Snapshots and events carry it; React drops events older than its snapshot and asks for a new snapshot when it sees a gap.
33. Does the frontend ever get raw database rows, or always shaped results (5.7)?
   **Decided:** shaped results only. Chats, runs and settings are the typed structs (Q6). Views return `columns` (name, type, format) plus rows as arrays (SPIKE-022); cell values are the other allowed `any` (JSON edge). React never sends SQL, never sees `_jenab_*` tables, and never gets a row the view didn't ask for.

## 10. Tests and logs
34. Only the standard `testing` package, or also testify?
   **Decided (2026-09-30):** the standard `testing` package plus `google/go-cmp` for struct diffs (approved). No testify, no goleak. Table-driven tests; helpers call `t.Helper()`.

   | Layer | What | How |
   |---|---|---|
   | Unit | `sqlguard`, `config`, `expr`, schedule functions, `limit`, the FTS query builder | table-driven |
   | Fuzz | SQL guard lexer, YAML config parsing, FTS query builder | Go fuzzing; they read untrusted input |
   | Integration | `store` on real SQLite in `t.TempDir()`; the agent loop with `provider/fake` and a real store | `go test` |
   | Spike regressions | SPIKE-007's 63 guard cases, SPIKE-008's crash tests, SPIKE-014's DST cases | permanent tests |
   | Scenarios | real models (TASK-001) | separate command, not in `go test` |

   `-race` runs in CI only for now: on Windows it needs cgo and a C compiler, and this machine has none.
35. `testing/synctest` (Go 1.25+) for code with goroutines and timers, such as the writer and the scheduler?
   **Decided:** yes, for the writer's 10:1 rule, `limit.Gate`, the coalescer, heartbeats, LLM stall timeouts (with `provider/fake`), the scheduler's minute check and project idle close. Fake time makes a 10-minute wait take milliseconds, and the test fails if a goroutine is left stuck, so no goleak. These tests use fast fake jobs; real-SQLite tests run outside synctest.
36. Logging with `log/slog`: where do logs go, and how are secrets redacted (6.7)?
   **Decided:** `log/slog` with the text handler, to `<data>/logs/`, rotated by size (10 MB × 5) by our own small writer. Info by default, Debug with the developer tools on; *Copy details* copies the matching lines.
   - Logged: IDs, kinds, timings, errors. Never message content, prompts or table data; prompts are seen only in the turn inspector (8.4).
   - `secret.Value` returns `[secret:NAME]` from `LogValue`, `String`, `GoString` and `MarshalJSON`, so a key can't reach a log, an error or a prompt by mistake. Only the provider's auth header calls `Reveal()`.
